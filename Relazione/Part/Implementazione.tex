campo \textit{club} del calciatore rappresenta la squadra reale ed è realizzata con un enum.

assegnati dal giornalista, la classe che rappresenta ciò è \textbf{Grade}.
In ogni giornata sono presenti più match ognuno dei quali è rappresentato 
dalla classe \textbf{Match}. Ogni match ha il riferimento ai due team coinvolti
ed una volta concluso ha un riferimento alla classe \textbf{Result}, ovvero il suo risultato.
La classe \textbf{LineUp} rappresenta la formazione schierata da un team per un match.
La classe \textbf{Scheme}, che rappresenta il modulo, è utilizzata per fare type mapping di \textbf{LineUp}. Anche per \textbf{LineUp} è presente una relazione mapppata
con \textbf{Jpa MappedBy} ed è quella con \textbf{Fielding}, che rappresenta lo schiaremento di un giocatore.
Infine è presente una classe \textbf{LineUpViewer} che implementa un'api sequenziabilizzabile e sicura
per instanziare una \textbf{LineUp}.

\subsection{Services}
Nel pacchetto \textit{Business} sono presenti i services, uno per ogni tipo di attore ed uno per il login.
I services utilizzano il \textbf{TransactionManager} per gestire le transazioni con il database.
In particolare vengono utilizzati i due metodi \textit{inTransaction} e \textit{fromTransaction}, il primo esegue la funzione
 passata all'interno di una transazione e non restituisce nulla mentre il secondo restituisce
 il valore della funzione passata. Inoltre attraverso il \textbf{TransactionContext} i services
 sono in grado di utilizzare i repository per effettuare le loro operazioni.
 I services presenti sono:
 \begin{itemize}
    \item \textbf{LoginService}: si occupa di effettuare le operazioni di login e registrazione.
    \item \textbf{UserService}: si occupa di gestire le operazioni di un utente base all'interno di una lega in cui partecipa.
    \item \textbf{AdminUserService}: si occupa gi gestire le operazioni esclusive di un admin all'interno di una lega.
    \item \textbf{NewsPaperService}: si occupa di gestire le operazioni di un giornalista all'interno di una lega.
 \end{itemize}

@Override
	public <T> T fromTransaction(Function<TransactionContext, T> code) {

		EntityManager em = emFactory.createEntityManager();
		EntityTransaction transaction = em.getTransaction();
		try {
			transaction.begin();
			T result = code.apply(new TransactionContext(
										new JpaLeagueRepository(em), 
										new JpaMatchRepository(em),
										new JpaPlayerRepository(em), 
										new JpaFantaTeamRepository(em), 
										new JpaGradeRepository(em),
										new JpaProposalRepository(em), 
										new JpaContractRepository(em), 
										new JpaResultsRepository(em),
										new JpaFieldingRepository(em), 
										new JpaLineUpRepository(em), 
										new JpaMatchDayRepository(em),
										new JpaNewsPaperRepository(em), 
										new JpaFantaUserRepository(em)));
			transaction.commit();
			return result;
		} catch (Exception e) {
			if (transaction.isActive()) {
				transaction.rollback();
			}
			throw e;
		} finally {
			em.close();
		}
	}

	@Override
	public void inTransaction(Consumer<TransactionContext> code) {
		fromTransaction((context) -> {
			code.accept(context);
			return true;
		});
	}
}
\end{lstlisting}

\subsection{Repositories}
I repository concreti estendono tutti il \textbf{BaseJpaRepository} ed implementano la relativa interfaccia.
Le query sono state implementate con le \textit{CriteriaQuery}, ciò ha permesso insieme
all'utilizzo del metamodello di avere un controllo a compile time sulle entità utilizzate nella query.

\begin{figure}
    \centering
    \includegraphics[width=\textwidth]{Resources/graficiUML/DALClassDiagram.png}        
    \caption{Dal class diagram.}
    \label{fig:Dal_class_diagram2}

Esempio di query effettuata tramite le \textit{CriteriaQuery}:
\begin{lstlisting}[language=Java]
@Override
	public Optional<FantaUser> getUser(String email, String password) {
    	EntityManager em = getEntityManager();
        CriteriaBuilder cb = em.getCriteriaBuilder();
        CriteriaQuery<FantaUser> query = cb.createQuery(FantaUser.class);
        Root<FantaUser> root = query.from(FantaUser.class);

        query.select(root).where(
                cb.equal(root.get(FantaUser_.email), email),
                cb.equal(root.get(FantaUser_.password), password)
        );

        return em.createQuery(query).getResultList().stream().findFirst();
	}
}
\end{lstlisting}

\subsubsection{Model-View-Presenter}
L'idea fondamentale del pattern (così come trattato in \cite{bettini2019tdd} e mostrato in Figura~\ref{fig:mvpDiagram}) è quella di organizzare l'interfaccia grafica in \emph{cellule} o \emph{contesti di presentazione}, ovvero aree deputate ad assorbire un insieme coesivo di use cases, e suddividere le responsabilità all'interno di ciascuna cellula fra due classi, \texttt{Presenter} e \texttt{View}, con questa razionale: 

\begin{itemize}
	\item il \textbf{Presenter} espone alla \texttt{View} metodi che hanno il compito di raccogliere le volontà dell'utente, e si serve delle primitive di presentazione esposte dalla \texttt{View} per organizzare la presentazione dell'informazione all'interno della cellula grafica
	\item la \textbf{View} espone al \texttt{Presenter} primitive di presentazione opportunamente implementate nell'ambiente grafico scelto, e inoltra le volontà recepite da parte dell'utente mediante i controlli grafici al \texttt{Presenter} tramite i medodi di ricezione che esso espone 
\end{itemize}

Appare evidente che - a netto dell'uso di interfacce per evitare l'accoppiamento diretto e favorire la testabilità - \texttt{Presenter} e \texttt{View} sono strettamente interconnesse. In effetti, come abbiamo premesso, esse realizzano congiuntamente una unica cellula di presentazione, ed è quindi particolarmente sensato pensare alla coppia come ad un \emph{duo} indissolubile. 
Di contro, esistono importanti limiti alla compenetrazione delle due componenti, che stanno alla base della solidità e dell'utilità del pattern:
\begin{itemize}
	\item \texttt{Presenter} è un componente \emph{logico} e dunque \emph{headless}, ovvero non è esposto alla nozione di interfaccia grafica, né materialmente attraverso tipi del toolkit grafico né concettualmente attraverso le nozioni di \emph{controlli grafici}. Espone metodi di ricezione delle volontà dell'utente che potrebbero essere validi per tipi di interfaccia utente radicalmente diversi fra loro. Infine, costituisce il ``volto pubblico'' della cellula presentativa verso il resto dell'applicazione 
	\item \texttt{View} è implementata in termini del toolkit grafico scelto, nel nostro caso \texttt{Swing}, e si fa carico di realizzare le primitive di presentazione e raccogliere le volontà dell'utente mediante i controlli ed i meccanismi offerti dal toolkit. Poiché le restanti cellule e l'applicazione nel suo complesso si rivolgono alla sua cellula mediante il solo \texttt{Presenter}, la \texttt{View} può e deve nascondere completamente i controlli grafici al suo interno
\end{itemize}
\texttt{Presenter} è il componente di livello più alto e più riusabile, e quello responsabile delle relazioni della cellula con il resto dell'applicazione. \texttt{View} costituisce semplicemente l'apparenza sensibile della cellula nel contesto del toolkit impiegato, ed ha interazioni soltanto con il suo \texttt{Presenter}.

\medskip
Al di là del particolare approccio prescritta da MVP, che può risultare spesso astruso e di difficile intuizione in fase di design, l'esperienza di sviluppo di questa GUI ci ha mostrato svariati indubbi vantaggi della scissione delle responsabilità presentative in alto e basso livello e della loro segregazione in tipi distinti. In effetti, anche quando siamo partiti con lo sviluppo di un unico componente ``fat'', col tempo siamo sempre arrivati alla conclusione che la scissione fosse sempre la strada corretta, anche a costo della complessità che introduce nel sistema. Nella nostra esperienza,

\begin{itemize}
	\item un unico componente ``fat'' è severamente limitato nella class inheritance. In \texttt{Swing}, esso è generalmente costretto ad ereditare da uno dei tipi concreti del toolkit come \texttt{JPanel} o \texttt{JFrame}. Di contro, ci siamo spesso giovati della possibilità di far ereditare al \texttt{Presenter} headless una classe astratta
	\item in un unico componente ``fat'' è facile cadere nella trappola di esprimere tutto il comportamento di presentazione in termini dei controlli grafici e dei particolari meccanismi ad essi associati nel toolkit. Questo approccio diventa difficile da gestire per qualsiasi comportamento non banale. Invece, la scissione in \texttt{View} e \texttt{Presenter} costringe ad identificare logica presentativa di alto e basso livello, ed implementare in termini del toolkit solo la seconda. In questo modo, le ``routine di presentazione'' nel \texttt{Presenter} sono completamente astratte dal toolkit, ed i meccanismi particolari del toolkit entrano in gioco nella \texttt{View} soltanto in ``primitive'' di presentazione, funzionalmente isolate e di respiro più ristretto
	\item un unico componente ``fat'' limita la velocità e la profondità dei test unitari. La scissione in \texttt{View} e \texttt{Presenter} permette al componente headless di essere istanziato velocemente. Inoltre, costringe a formulare le interazioni reciproche nel duo in termini di \emph{interfacce}, che assorbono esaustivamente le proprietà di interesse dei due componenti e le rendono perfettamente verificabili in fase di test 
\end{itemize}

\subsubsection{Aspetti notevoli dell'implementazione}
Nel corso della realizzazione della GUI, che si è arrestata al solo pannello di selezione della formazione, abbiamo dovuto adottare scelte specifiche per assorbire la complessità delle caratteristiche dell'interfaccia grafica che avevamo in mente. 
Riassumiamo in questa sezione quelle più significative.

\paragraph{Modularità}
Quando ci si trova a gestire contesti di presentazione complessi è intuitivo e, crediamo, corretto cercare di realizzarli mediante \emph{composizione} di \emph{moduli} singolarmente più semplici. Questa modularità ha vantaggi evidenti per la testabilità, leggibilità, manutenibilità del codice.
Tuttavia, una criticità intrinseca dell'impiego del pattern MVP è il fatto che esso scinde \emph{una} unica cellula presentativa in \emph{due} classi. L'idea stessa di \emph{composizione} risulta dunque problematica e va gestita opportunamente.

Quello che abbiamo fatto nella nostra implementazione è stato sostanzialmente replicare - in maniera non codificabile nei tipi e dunque dichiaratamente fragile - la composizione in entrambe le dimensioni headless e grafica di MVP, come raffigurato in questo schema:

Il tipo headless di una cellula si relaziona con il tipo headless del modulo/dei moduli di livello inferiore mediante interfaccia \texttt{Delegate}. Il tipo grafico di una cellula \emph{contiene graficamente} (secondo la semantica del toolkit impiegato) le componenti grafiche del modulo/dei moduli di livello inferiore, ma queste gli sono opache. Dunque, si preserva l'invariante MVP che l'interazione fra componenti applicativi passa esclusivamente dalla componente headless, e si rispettano i principi di Dependency Inversion ed Interface Segregation.

\smallskip
La nomenclatura delle classi differisce leggermente da quanto mostrato in figura. Le diciture \texttt{Presenter} e \texttt{View} sono state riservate alle interfacce dei soli componenti di ordine massimo: per tutti gli altri, le interfacce seguono i suffissi \texttt{-Delegate}, \texttt{-Controller} e \texttt{-Widget} come in figura. Invece, le classi concrete hanno un prefisso \texttt{Swing-} per i componenti grafici e \emph{nessun prefisso o suffisso} per i componenti headless.

\paragraph{Strategie di testing}\label{par:guiTesting}
Lo schema di composizione appena esposto va naturalmente nella direzione di facilitare il testing unitario, in quanto mantiene distinte le componenti headless e grafiche e prevede interfacce per ogni interazione.

Tuttavia, in questo schema un singolo componente concreto si trova ad implementare molteplici interfacce - nel caso di un componente headless, almeno due: quella ``verticale'' verso il componente grafico e quella ``orizzontale'' verso il componente headless di ordine superiore. Nel nostro codice non è raro che questo numero sia ancora più elevato, a causa di ulteriori collaborazioni che interessano il componente headless.

In questo contesto ci è sembrata particolarmente adatta la possibilità offerta da \textbf{JUnit 5} di raggruppare i test, grazie alla facility dei \emph{\texttt{@Nested} testcases}. In questo modo, siamo stati in grado di organizzare le asserzioni per ``mandato'' o interfaccia implementata, e rendere perfettamente leggibile questa strutturazione grazie al comportamento di \texttt{@DisplayName} lungo un albero di nesting.
Inoltre, Junit 5 offre una integrazione con \textbf{Mockito} particolarmente espressiva ed efficiente. Ci siamo serviti pesantemente delle primitive di mocking e degli eccellenti strumenti diagnostici di questo framework.

Il framework di testing grafico che abbiamo usato, seguendo il suggerimento di \cite{bettini2019tdd}, è \textbf{AssertJ Swing}, che offre semplici ed efficaci API per l'interazione grafica programmatica.


\paragraph{Inizializzazione vs Istanziazione}\label{par:initVsInst}
Un paradigma che ci è apparso importante rispettare nello sviluppo di un componente grafico è stato quello di \emph{rimuovere per quanto possibile la configurazione dall'istanziazione}: in quest'ottica, il costruttore si occupa solo di istanziare i sotto-componenti grafici ed assemblarli correttamente, ma non conferisce al componente risultante nessuna \emph{proprietà utile}, come ad esempio uno \emph{``stato iniziale''}. Questa è invece responsabilità di appositi metodi d'istanza che possiamo chiamare di \emph{inizializzazione} o \emph{configurazione}.

Questo semplice principio obbliga i client del componente stesso a dipendere sempre dalle sue API di configurazione, anche in casi in cui si sarebbe preferito sollevarli da tale incombenza assorbendo quanta più configurazione possibile nell'istanziazione.
Tuttavia, ci siamo sempre convinti che questa limitata pesantezza nei client fosse ampiamente compensata dalla maggior pulizia e velocità che il principio porta nel testing unitario del componente grafico: soltanto quando l'istanziazione è totalmente disaccoppiata dalla configurazione, il componente istanziato è un autentico ``foglio bianco'', ed i metodi di configurazione possono veramente essere testati in isolamento.


\paragraph{Uso di WindowBuilder come editor WYSIWYG}
Al fine di fare design grafico dei componenti GUI più agevolmente, ci siamo serviti dei tool raccomandati da \cite{bettini2019tdd}, ovvero l'editor WYSIWYG WindowBuilder disponibile come plugin di Eclipse. 

Una caratteristica sicuramente ottima di WindowBuilder è il fatto che lavora direttamente sul codice Java, senza bisogno di generare file ``di layout''.
Tuttavia, WindowBuilder ha la limitazione significativa di non eseguire il codice dei costruttori nativamente nella JVM, ma basare il rendering su un \emph{parsing} del codice stesso. Questo significa che, in pratica, alune istruzioni del corpo del costruttore non saranno eseguite.

La documentazione di WindowBuilder non chiarisce quali sono le tipologie di istruzioni supportate a render-time. Col tempo ci siamo resi conto che il comportamento di WindowBuilder sembra variare a seconda che il costruttore sia quello del tipo renderizzato o di un tipo diverso: per tipi diversi da quello renderizzato, WindowBuilder sembra eseguire tutte le istruzioni. In ogni caso, abbiamo dovuto documentare in ogni tipo grafico le limitazioni del rendering per quel tipo.

In ogni caso, un tool WYSIWYG si limita a fare rendering del costruttore. Ciò significa che qualunque comportamento di configurazione espresso in metodi d'istanza non potrà essere esaminato e validato graficamente - un chiaro svantaggio dell'applicazione del principio \nameref{par:initVsInst}.


\paragraph{Istanziazione di design pubblica e privata}\label{par:pubPrivInst}
Come conseguenza della modularità, si pone il problema se includere o meno i moduli ``figli'' nel rendering in WindowBuilder di un modulo ``padre''. A nostro avviso, questa inclusione permette di aggiustare le caratteristiche visive del modulo padre in maniera consistente con quelle dei moduli figli, e dunque rende ancora più sensato e conveniente l'uso un tool WYSWYG.

A questo punto, una nuova opportunità arriva dal fatto di poter distinguere il rendering che WindowBuilder fa di un modulo quando si fa design del modulo stesso da quello che ne fa nel design di moduli ``padre''. In effetti, nel design di un modulo possono essere utili annotazioni e appunti grafici che però si preferisce omettere nel rendering ``pubblico'' di quel modulo, ovvero quello che viene adottato nel design dei moduli che lo contengono.

La nostra soluzione è stata fare overloading di costruttori con diversa visibilità, documentando opportunamente, e cercare di implementare il massimo riuso internamente ai due punti di istanziazione. In questo modo, nel design del modulo stesso WindowBuilder adotta sempre il costruttore privato, mentre nel design di un modulo ``padre'' può essere diretto verso i costruttori pubblici dei moduli ``figli''.

\paragraph{Gestione delle immagini raster}
Una caratteristica che abbiamo sempre voluto conferire alla nostra GUI, per definizione del tipo di applicazione che riveste, è la presenza di immagini: ad esempio, nella scelta della formazione ci è sembrato piuttosto obbligato usare una immagine di un campo da calcio come sfondo su cui disporre i selettori dei giocatori secondo gli schemi calcistici.

Una limitazione sicuramente ragionevole ma piuttosto penalizzante di Swing è il fatto che non si fa carico di gestire il resizing dinamico di una risorsa raster: in altri termini, una volta caricata in memoria una immagine \texttt{.png} e passata a Swing per costruire una \texttt{JLabel}, Swing non farà più alcun intervento sulle dimensioni dell'immagine durante il ciclo di vita della \texttt{JLabel}. Questo porta ad una certa problematicità nel trattamento di risorse raster quando Swing gestisce il \emph{sizing} lungo l'albero di composizione grafica ingaggiando i \emph{\texttt{LayoutManager}s}. Il fatto che \texttt{LayoutManager}s diversi abbiano atteggiamenti completamente opposti verso i requisiti di size dei componenti figli non fa che peggiorare il quadro.

La strategia che ci è parsa migliore per risolvere il problema del sizing delle risorse raster, anche se indubbiamente non la più flessibile, è stata quella di consegnare a Swing le immagini nel loro scaling \emph{definitivo} - che quindi deve essere attualizzato sulle dimensioni dello schermo e perfettamente armonizzato fra tutti i componenti raster della GUI - e impedire che le dimensioni della GUI stessa possano cambiare una volta avviata l'applicazione. Quest'ultimo requisito non è, in verità, molto limitante, ed era anzi una proprietà che avremmo comunque trovato utile per il tipo di GUI che avevamo in mente. Il primo requisito chiede invece una collaborazione fra tutti i componenti della GUI per gestire l'istanziazione con scaling armonizzato di tutte le risorse raster. Nella pratica, si è seguito un approccio in cui i componenti di ordine massimo fanno da ``source of truth'' e quelli di ordine inferiore \emph{derivano} le proprie indicazioni di scaling in base a fattori di proporzione, rispettando così la dipendenza logica.\footnote{Una diversa soluzione sarebbe stata produrre le risorse raster già nelle opportune proporzioni: a quel punto, si sarebbe soltanto dovuto attualizzarne le dimensioni a quelle dello schermo. Questo approccio ci è sebrato inaccettabile perché volevamo la massima libertà nella produzione delle immagini, in modo da poterci servire dei LLMMs}

Infine, è stato molto utile centralizzare le responsabilità di istanziazione con scaling delle risorse raster in una unica classe, \texttt{ImageManager}, anche al fine di ottimizzare gli accessi a disco. Con una formulazione assolutamente non standard del pattern Singleton si è miracolosamente riusciti a rendere \texttt{ImageManager} compatibile con WindowBuilder.


\subsubsection{Considerazioni finali}

\paragraph{Uso di un framework per Dependency Injection}
Un design modulare della GUI ha come immediata conseguenza la proliferazione dei tipi. Per onorare il Dependency Inversion Principle, abbiamo adottato \emph{dependency injection} su tutte le collaborazioni, facendo in modo che le collaborazioni vengano sempre istanziate all'esterno e passate ad un tipo tramite costruttore o setter.

Questo non è chiaramente stato possibile nei costruttori grafici design-time, nei quali, come discusso in \nameref{par:pubPrivInst}, è auspicabile una istanziazione ``collassata'' che contenga già istanze delle ``dipendenze'' (ovvero delle apparenze grafiche dei moduli composti).

Per semplificare il codice dei costruttori grafici design-time, nonché quello di lancio dell'applicazione qualora l'avessimo completata, sarebbe stato decisamente utile un framework per automatizzare la dependency injection, come \textbf{Google Guice} suggerito da \cite{bettini2019tdd}.
Un ambito di assoluto interesse sarebbe stato, a quel punto, la compatibilità fra il framework e WindowBuilder.

\paragraph{Obsolescenza dello stack}
Lo stack tecnico di cui ci siamo serviti per sviluppare la GUI, ovvero Swing, AssertJ Swing e WindowBuilder, aveva il pregio di essere minuziosamente descritto in \cite{bettini2019tdd}. Tuttavia risulta essere estremamente datato, e non poco tempo ci è costato risolverne gli aspetti di obsolescenza. In particolare

\begin{description}
	\item[Swing] è stato un tool fondamentale per lo sviluppo di GUI in Java, ma attualmente non gode più di vasta adozione. Ne consegue che per molte delle features introdotte per ultime è disponibile poca documentazione: ad esempio, per il layout manager Spring
	\item[WindowBuilder] ha le stesse problematiche di adozione di Swing. Inoltre, proprio per le ultime features di Swing il supporto al design è chiaramente incompleto: ad esempio, il layout manager Spring non ha quasi nessun ausilio grafico, a differenza di altri come GridBag, e WindowBuilder non ne supporta altre API all'infuori di \texttt{putConstraint()}
	\item[AssertJ Swing] non è più mantenuto da qualche anno. Vista l'enorme utilità delle features di JUnit 5 nel nostro testing della GUI, come già detto in \nameref{par:guiTesting}, una caratteristica che abbiamo dovuto necessariamente aggiungere manualmente è stata l'integrazione con JUnit 5, attraverso un nuovo testcase di base che facesse porting verso JUnit 5 del vecchio \texttt{AssertJSwingJUnitTestCase} basato su JUnit 4.
